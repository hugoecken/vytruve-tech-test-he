# Repository Spec Kit Constitution

## Repository Authority First

`AGENTS.md` governs every agent and routes each task to the repository's authoritative policies, overlays, current
sources, and runbooks. This constitution is only an adapter and never overrides or duplicates those authorities.

## Specification And Runtime Authority

An accepted `specs/<feature>/spec.md` snapshot owns future observable intent. Its matching `plan.md` translates that
intent into the current architecture, and `tasks.md` is only a derived checklist. Current contracts, source code, and
tests remain authoritative for delivered behavior.

## Roadmap And GitFlow Authority

The task system selected by repository guidance exclusively owns acceptance, priority, dependencies, claims, scope,
execution state, review, and completion. The selected Git workflow owns task branches and pull requests. Spec Kit must
not create a competing branch, issue, task, status, review, release, or merge control plane.

## Source Gates And Validation

Every phase loads repository guidance, uses its real application, contract, documentation, and design boundaries, and
applies the selected product, security, architecture, and validation gates. Missing or ambiguous authority fails
closed.

## Managed Artifacts And Local State

Core Spec Kit skills, scripts, templates, workflows, and manifests remain generated and upgradeable. Repository
adaptation uses only supported extension mechanisms. Local active-feature selection remains workstation state and
never becomes shared claim or task state.

## Governance

Changes require the ownership, scope, planning approval, review, and release gates selected by repository guidance.
Runtime behavior cannot be changed through this constitution.
